5. 火力区配置

火力区范围不是自动跟着 theaters[].bounds 变化的。
如果改四区地图范围，需要同步改各参数文件里的 fire_pool_bounds。

位置：
- 26D-A: configs/theater_params/henan_1.json
- 26D-B: configs/theater_params/henan_2.json
- 27-A: configs/theater_params/guangdong_1.json
- 27-B: configs/theater_params/guangdong_2.json

字段：
vehicle_scoring.fire_pool_bounds

当前逻辑：
- 每个旅的火力区暂定为该旅 bounds 的左半边。
- 车辆评分时，如果车辆当前位置 lon/lat 落入 fire_pool_bounds，就加 fire_pool_bonus。
- fire_pool_bonus 当前为 8.0。

计算规则：
fire_pool_bounds = [
  区域 lon_min,
  区域 lat_min,
  (区域 lon_min + 区域 lon_max) / 2,
  区域 lat_max
]


6. 启动脚本

一键全量启动：
scripts/start_server_all.sh

当前 start_server_all.sh 会做：
1. cd 到项目根目录。
2. 默认使用 configs/deployment_topology.local_192.json。
3. 如果存在 .venv/bin/activate，自动 source。
4. 如果加 --open-code，则打开 VS Code；默认不打开。
5. 执行 prepare。
6. 启动 scheduler。
7. 启动车辆 gateway 和车辆进程。
8. 启动贮备库 gateway 和贮备库进程。

命令：
bash scripts/start_server_all.sh

或指定配置：
bash scripts/start_server_all.sh \
  --deployment-config configs/deployment_topology.local_192.json

快速重启：
scripts/restart_runtime_no_prepare.sh

该脚本不会 prepare，只会：
1. down 停进程。
2. 清 logs、.run/logs、result/message_capture。
3. 用已有 result/configs 重启 scheduler、vehicles、depot。

重要：
- 改地图范围、端口、车辆数、贮备库数之后，不要只跑 restart_runtime_no_prepare.sh。
- 必须跑 start_server_all.sh 或手动 prepare。


7. prepare 的意义

prepare 会重新生成运行所需配置，包括：
- result/configs/scheduler_debug.json
- result/configs/schedulers/*.json
- result/configs/vehicles/*.json
- result/configs/depot_gateway.json
- result/configs/depots/*.json
- result/theaters/<theater_id>/data/road_graph_shp_demo.json
- result/theaters/<theater_id>/data/special_points_shp_demo.json
- result/theaters/<theater_id>/configs/scheduler_debug.json
- result/theaters/<theater_id>/configs/vehicles/*.json

只改 configs/deployment_topology.local_192.json 不 prepare 的后果：
- 运行进程可能仍使用旧 result/configs。
- 四区地图范围可能没有实际生效。
- 车辆/调度/贮备库端口可能还是旧配置。

12. 当前四旅服务器测试出现的问题

用户描述的现象：
- 四个战区测试时，每个 logs 后面出现红色乱码。
- 调度没有发出上下文给车辆。
- 调度收到了 VEHICLE_DIAN，但是只有 3 个点。
- 调度发了任务包响应和 REQUEST_DIAN。
- 车辆收到了 VEHICLE_CONTEXT。
- 车辆没有发分数。
- 暂时没有完整文件可以检查。

当前初步判断：
- 最大概率不是车辆端先坏，而是调度端没有满足发送候选上下文的前置条件。

调度发送上下文的门槛：
mvs/scheduler/scheduler_app.py

关键函数：
- _on_dian_context()
- _maybe_send_vehicle_scoring_context_to_model()
- _send_vehicle_scoring_context_to_model()

逻辑要求：
- 发射点数量 >= 本调度车辆数
- 隐蔽点存在
- 车辆点数量 >= 本调度车辆数
- 贮备库点存在
- 贮备库已投影成功

如果某个调度只收到 3 个 VEHICLE_DIAN，而 expected_vehicles 是 36 或 33，则调度会一直等待，不会发送：
- TIME_BACKPLAN_CONTEXT
- VEHICLE_CANDIDATE_CONTEXT

车辆没有这两个上下文时，即使收到 VEHICLE_CONTEXT，也可能不会回分数。

14. 当前最可能原因排序

原因1：四区 bounds 过滤掉了大部分 VEHICLE_DIAN
- 调度收到点位后会按自身 theater bounds 过滤。
- 如果车辆点坐标不在对应旅 bounds 内，就被丢掉。
- 结果会出现 VEHICLE_DIAN 只剩 3 个。

需要检查：
- logs/scheduler_*_events.jsonl 中 dian_context_received 的 count 和 total。
- vehicle_scoring_context_waiting_dian 里的 vehicle_count / vehicle_expected。
- message_capture/scheduler/*/recv 里 VEHICLE_DIAN 原始数据数量。
- 对比过滤前后数量，如果原始多、日志 count 少，就是 bounds 过滤问题。

原因2：改了配置但没有 prepare
- start_server_all.sh 会 prepare。
- restart_runtime_no_prepare.sh 不会 prepare。
- 如果改坐标后用 restart_runtime_no_prepare.sh，运行时可能还是旧配置。

原因3：模型分组名和本系统四旅 tag 不一致
- 当前配置使用 26D-A、26D-B、27-A、27-B。
- 如果模型仍然只按 26D/27 或旧字段发点位，调度可能收到的数据不完整。

原因4：27-B 当前只有33辆，模型或节点按36辆期待
- 当前配置是 141 总车。
- 如果外部按144总车发请求/选车，27-B 会不一致。

原因5：红色乱码
- 可能是日志最后一行不是完整 JSONL。
- 也可能是异常栈、进程中断、并发写、VS Code JSON Lines 高亮异常。
- 它更像结果，不一定是根因。

17. 重要提醒

不要把 VEHICLE_CONTEXT 和 VEHICLE_CANDIDATE_CONTEXT 混为一类：
- VEHICLE_CONTEXT 是模型/节点发来的车辆状态或评分触发信息。
- VEHICLE_CANDIDATE_CONTEXT 是调度发给模型，再由模型转发给车辆的候选上下文。

车辆正常快速评分需要：
- 收到 TIME_BACKPLAN_CONTEXT。
- 收到 VEHICLE_CANDIDATE_CONTEXT。
- 收到 VEHICLE_CONTEXT 触发评分。

如果只有 VEHICLE_CONTEXT，没有前两个上下文，车辆不会正常回分。
